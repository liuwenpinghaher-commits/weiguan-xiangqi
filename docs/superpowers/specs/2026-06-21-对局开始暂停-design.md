# 围观象棋 · 对局开始/暂停设计

- 日期:2026-06-21
- 状态:已与用户确认设计,待写实现计划
- 一句话:给对局页加显式「开始 / 暂停 / 继续」控制——进页不自动开局,点开始才连服务器开局;暂停是**整局总开关**(棋盘、AI、观棋者弹幕、语音、冷场闲聊一起停),继续恢复。

## 背景与现状

对局页(`web/src/pages/PlayPage.tsx`)现在:进页即自动连 WS + 自动发 `{type:'new'}` 开局;观棋者弹幕/语音/冷场闲聊由**服务端**驱动持续进行;无任何「暂停」概念。`GameStatus = 'connecting'|'waiting'|'playing'|'over'|'error'`。冷场闲聊由 ws-server 的 idle 定时器按 `chat.idleIntervalMs` 周期对 `lastGameId` 触发;弹幕由 `move`/`say`/`idle` 刺激经 `ChatEngine.onStimulus`→`emit`→sockets 广播。

## 用户已确认的关键决策

1. **暂停范围 = 整局总开关**:暂停时棋盘不可走、AI 不接、观棋者弹幕与语音停、冷场闲聊停;开始/继续恢复。一个总开关。
2. **进页不自动开局**:进页处于「未开始」态(棋盘锁定、无弹幕语音),点「开始」才连服务器并开局。
3. **实现取舍 = 服务端感知暂停**:WS 发 `{type:'pause'}`/`{type:'resume'}`,服务端停冷场定时器、暂停期间不触发/不广播弹幕、忽略走子。避免暂停期间空耗 LLM/TTS,继续时无积压。(否决纯前端方案:服务端会在后台继续生成冷场闲聊、空耗 LLM。)

## 架构

### 1. PlayPage 状态机扩展
`GameStatus` 增加 **`idle`(未开始)** 与 **`paused`**:
- 进页 → `idle`:不连 WS、不开局,棋盘锁定,无弹幕语音,显示「开始」。
- 「开始」(idle/over 时)→ 连 WS + 发 `{type:'new', mode, humanSide, startFen}` → 收到 `started` → `playing`。
- 「暂停」(playing 时)→ `paused`:发 `{type:'pause', gameId}` + 调前端 `stopVoice()` 立即停声 + 锁棋盘,显示「继续」。
- 「继续」(paused 时)→ 发 `{type:'resume', gameId}` → `playing`。
- 状态栏旁单个主按钮随状态切换文案:`idle`/`over`→「开始」、`playing`→「暂停」、`paused`→「继续」。

模式/执方选择:在 `idle` 态只 setState、不重开;「开始」时带上当前 mode/side。`playing` 态改模式/执方仍走现有「重开」逻辑(不变)。专项陪练入口(读 `sessionStorage` 的 sparring fen/side)仍直接开始——它是别处的显式动作,绕过 idle 闸门。

### 2. ws-server 暂停支持
- 维护 `pausedGames: Set<number>`。
- 处理两类新 WS 消息:`{type:'pause', gameId}` → `pausedGames.add(gameId)`;`{type:'resume', gameId}` → `pausedGames.delete(gameId)`。
- **冷场定时器**:回调里若 `lastGameId === null || pausedGames.has(lastGameId)` 则跳过(不触发 idle 刺激)。
- **弹幕抑制**:`move`/`say`/`idle` 路径在调用 `chat.onStimulus(...)` 前,若该 `gameId` 在 `pausedGames` 中则跳过(不生成、不广播)。
- 暂停期间收到 `{type:'move'}` → 直接忽略(前端已锁棋盘,服务端双保险)。
- `say` 在暂停期间:既不回显也不触发刺激(整局停)。

### 3. 前端语音急停
`web/src/voice/server-tts.ts` 新增 `stopVoice()`:停掉当前 `<audio>`(`pause()` + 清 `src`)并清空预合成队列(`queue = []`),使正在播放/排队的语音立即静。暂停时由 PlayPage 调用。

## 数据流

```
[idle] 点开始 → connect WS → send {new} → started → [playing]
[playing] 点暂停 → send {pause,gameId} ; stopVoice() ; 锁棋盘 → [paused]
   (服务端:pausedGames.add → idle 定时器跳过该局 + move/say/idle 不再触发弹幕)
[paused] 点继续 → send {resume,gameId} → [playing]
   (服务端:pausedGames.delete → 恢复)
```

## 错误处理

- `paused`/`idle` 态:棋盘 `disabled`,`onSay`/走子被前端拦截(不发 WS)。
- 暂停期间服务端忽略 `move`(防御);`pause`/`resume` 的 `gameId` 非法(非 number)→ 忽略。
- 断线重连:现有重连逻辑保留;重连后若曾 `paused`,前端按当前状态显示(暂停态不自动续——简单起见刷新/重连回到由前端状态决定;不做暂停持久化,见 YAGNI)。

## 测试策略

- **ws-server(集成,真实 WS)**:① 开局后发 `{pause}` → 再发 `{move}`/`{say}` → 在窗口内**不**收到任何 `chat` 帧;② 发 `{resume}` 后再 `{say}` → 恢复收到 `chat`;③ idle 定时器在 paused 时不触发(可缩短 idleIntervalMs 注入后观察无 idle chat)。
- **前端 server-tts**:`stopVoice()` 纯逻辑可单测(调用后队列清空;不依赖真实 audio——把 audio 元素访问包成可注入或在 node 下跳过 DOM 部分,仅断言队列状态)。
- **PlayPage 状态机**:`idle→playing→paused→playing` 转换走 typecheck+build + 人工目检(组件在 node 环境不可渲染测)。
- 既有 282 server + 32 web 测试不破。

## 风险与权衡

- **服务端 emit gate 的放置**:抑制点选在「调 `onStimulus` 前按 gameId 跳过」,比改 `ChatEngine.emit` 更局部、风险小(ChatEngine 不需知道暂停)。
- **暂停期间的在途广播**:服务端在 pause 落地前可能已 emit 了一两条(竞态);前端 `paused` 态可顺手忽略收到的 `chat`(双保险),配合 `stopVoice()` 保证听感上即时静。
- **不做**:计时/对弈钟、多局并行暂停、暂停状态持久化(刷新回 idle)。
