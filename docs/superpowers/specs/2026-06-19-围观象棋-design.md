# 围观象棋 · AI 陪练与观棋伙伴 — 方案设计文档

- 日期:2026-06-19
- 状态:设计已与用户确认,待评审后转实现计划
- 定位:**Web 优先(后续移动 app)、个人单机自用、云端语音 + 云端 LLM、本地后端托管开源象棋引擎**

---

## 1. 产品愿景(一句话)

一个像"老棋友茶馆"一样的中国象棋工具:有一位**记得你、懂你、会暗中带你成长**的 AI 棋手,旁边还围着 2-3 个**性格迥异、各帮各踩**的观棋者;全程能语音聊天;它持续诊断你的棋力短板、生成针对性训练,并把你每一局沉淀成可回看的成长轨迹。

设计原则:**棋力交给专门引擎,表达与人设交给 LLM,我们只写"导演层 / 人设层 / 记忆层 / 诊断层"这点真正独特的逻辑**;其余全部复用成熟开源件,把自有代码量压到最小。

---

## 2. 关键决策(已与用户对齐)

| 维度 | 决策 |
|---|---|
| 平台 | Web 优先,成熟后开发移动 app(后端 API 复用) |
| 部署/用户 | 个人单机自用,数据全本地(SQLite),无账号体系 |
| 语音 | 云服务优先(实时 STT/TTS,多音色),架构上留可替换接口 |
| LLM 大脑 | 云端 API(中文表达与人设质量最高,集成最省代码) |
| 棋力来源 | 开源引擎 Pikafish(UCI),非 LLM |
| AI 棋手定位 | 陪练控盘 + 拟人对手,**两者皆有**,可切换 |
| 范围 | **一次性最优、不分阉割版**;里程碑仅作实现顺序 |
| 角色记忆 | **棋手 + 观棋者均具备跨会话长期记忆**(核心需求) |
| 后端语言 | Node(与前端同语言,最省代码) |

## 4. 复用的开源件(自有代码最小化)

| 能力 | 选型 | 说明 |
|---|---|---|
| 棋力引擎 | **Pikafish** | 当前最强开源中国象棋引擎,Stockfish 派生,UCI 协议;需配套 NNUE 权重文件。提供 `Skill Level` / `UCI_LimitStrength` / `UCI_Elo` / `MultiPV` 等参数 —— 这是控盘的技术支点。 |
| 规则 / 着法生成 / 合法性 | 开源象棋规则库(JS) | 负责合法着法、将军/将死判定、重复局面与和棋规则。成熟度需在实现期评估,必要时以 Pikafish 的 `go perft` / 局面校验兜底。 |
| 棋盘渲染 | 开源棋盘组件(chessground 象棋适配 / xiangqi 棋盘组件) | 拖拽落子、走法高亮、上一步标记、翻转棋盘。 |
| 局面 / 棋谱格式 | 象棋 FEN + UCI 着法 + ICCS/WXF 记谱 | 行业标准,Pikafish 原生使用;导入导出走标准格式以便与其他软件互通。 |
| 存储 | SQLite(better-sqlite3) | 单文件、零运维、个人单机最佳。 |
| 图表 | 开源图表库 | 成长曲线、雷达图(弱点画像)、阶段失误率柱状。 |
| LLM | 云 API SDK | 角色对话、讲解、诊断措辞、成长报告。 |
| 语音 | 云实时 STT/TTS SDK | 多音色映射到不同角色;封装为可替换的 `VoiceProvider` 接口,未来可切本地开源模型(whisper.cpp / 开源 TTS)。 |
| 前端框架 | Vite + React + TypeScript | 默认现代栈,响应式为移动端铺路。 |
| 后端框架 | Node + Fastify(+ ws) | 与前端同语言;子进程管理 Pikafish。 |

**自有核心代码仅四块**:① 导演控制器 ② 角色人设 + 记忆层 ③ 诊断/成长分析的标注与画像 ④ 实时对局编排(WebSocket)。

## 5. 核心子系统设计

### 5.1 引擎管理(Engine Manager)
- 启动时拉起 Pikafish 子进程,用 UCI 协议通信;封装 `analyze(fen, {multipv, depth|movetime})` 返回候选着法列表 `[{move, scoreCp, pv}]`。
- 同时服务于:对弈(选着)、诊断(算每步丢分)、训练(出题/校验)。单实例 + 请求队列,避免并发串话。
- 接口契约:输入象棋 FEN,输出着法及厘兵评分(centipawn);上层不关心引擎内部。

### 5.2 导演控制器(Director)— 控盘与心理(方案灵魂)
**不修改引擎,只做"选着策略"**:

- **拿候选**:对当前局面用 `MultiPV=N` 取 N 个着法及评分。
- **陪练模式**:实时估算双方胜率(由引擎评分映射),目标把对局压在"跳一跳够得着"的胜率带(用户略优、需努力)。从候选中按目标挑选着法:不一定走最优,允许"合理的次优/小失误",引导用户抓机会。
- **拟人对手模式**:加载棋风档案(激进弃子 / 保守缠斗 / 残局机器 …),用"目标 Elo + 风格权重"对候选着法采样,输赢自然真实。
- **两模式同框**,一个开关切换;参数可调(目标 Elo、控盘强度)。
- **防穿帮(关键)**:控盘时禁止"明显送大子"等一眼假的着法;失误必须藏在合理变化里、像真人手滑而非故意放水;限制单步让分幅度;连续让步要分散。否则陪练体验立刻崩塌。

**心理状态 —— 诚实版**:真实情绪不可直接读取,系统基于**可观测行为代理**推断:落子时长、长考、连胜/连败、悔棋频率、失误连发。导演据此微调(连败→悄悄松一档维持心流;连胜上头→加点压力)。
> 文档与产品文案中明确声明:这是**基于行为信号的推断,非读心**。

**优化目标:防流失/参与度,而非仅"防穿帮"**(深度研究修正项)
"不明显放水"只是**约束条件**,不是目标本身。导演的顶层判据应是"**让玩家保持投入**"(借鉴 EDDA / Engagement-driven DDA 思路):用行为信号(连败挫败、连胜无聊、长考、悔棋、想离开的迹象)估计参与度趋势,以"维持心流、防止流失/弃局"为优化目标来调难度;防穿帮、Elo 波动幅度上限等作为约束。这比单纯"别被看出放水"更贴近最终目的。

### 5.3 角色编排 + 长期记忆(Personas + Memory)
**角色清单(可配置):**
- **AI 棋手**:与你对弈、复盘讲解;有自己的口吻与脾气。
- **观棋者 2-3 个**,人设互异、**帮踩对象不同**,例如:
  - 「毒舌老炮儿」—— 专踩你的软招,嘴硬心热。
  - 「棋协教练」—— 温和、偏向你这边,给建设性提示。
  - 「起哄网友」—— 墙头草,谁优势踩谁,负责活跃气氛。
- 每个角色:一套人设 system prompt + 独立云 TTS 音色;实时结合局面评分,生成简短点评(弹幕式),语音播报。

**角色档案(每个角色都是个"完整的人",而非功能标签)**
每个角色由一份结构化档案定义,既喂给 LLM 做人设,也驱动行为差异:
- **棋力档**:各人棋力不同(如老炮儿业余强、教练专业级、网友半瓶醋),决定其点评的准确度与自信度(见下"会看走眼")。
- **身世背景**:职业与人生经历(如"退休机修工,在工人文化宫杀了三十年棋""体校出身的青年教练""刚毕业的程序员棋迷")。背景影响口吻、用词、关心的话题、讲得出的故事。
- **话题范围**:不只聊棋——能扯生活、行业、年代往事、家长里短等有趣闲篇,该插科打诨时插科打诨,让茶馆气氛真实。背景给了他"聊得出什么"。
- **口吻与脾气**:语气、口头禅、急脾气/慢性子、嘴硬/温和。
- **帮踩倾向**:默认偏帮/偏踩的对象(但会被局势与情绪自然改变,非死规则)。

> 这些档案是**可配置项**(一份角色配置 + 长期记忆),改档案就换一桌棋友,不改代码。首版预置 1 位 AI 棋手 + 2-3 位观棋者,各档案饱满成型。

**懂棋、会讲、也会看走眼(关键:角色是"真懂棋的人",不是复读机)**
- **真有料**:每个角色有自己的棋学底子,会抛具体棋招(如"这步该飞相固防""中炮过河车是老套路了"),会讲**棋坛掌故与妙手轶事**(名局、名手、典故),聊天像懂行的老棋友而非客服。素材来自 LLM 知识 + 注入的当前局面/历史,口吻由人设定。
- **会犯错、有疏漏**:角色的判断**不等于引擎真理**。我们给不同角色设不同"棋力档与自信度":有的常看准、有的偶尔误判、起哄型最容易想当然。系统把引擎评分作为**事实底牌**只用于"是否制造分歧",**不强制角色说对**——角色照人设发挥,该走眼就走眼。这种偶尔的错,正是真实感来源。
- **用机制制造差异,而非只靠 prompt(深度研究警示)**:研究实测同一 LLM 套不同角色 prompt,底层表征可高度雷同(余弦相似度 ~0.888)——**光靠人设文字,几个棋友可能给出趋同棋评**。对策是把"棋力差异"做成**机制差异**:按角色棋力档,给他看到的引擎读数深浅/含噪不同(弱角色只给浅层、带噪声的评估,甚至只给局部信息),其判断便**真的**不同、真的会看走眼,而非演出来的。这是化解"人设趋同"的关键。上线后需做小规模盲测验证角色可区分度。
- **自然涌现,不写死**:错与对、谁帮谁、何时拌嘴,**不靠规则脚本**。各角色看到**最近的聊天上下文** + 当前局面 + 自己对玩家/对其他角色的态度记忆,由 LLM 自由反应。于是"A 夸你这步好、B 偏说是俗手、教练打圆场"这类**拉踩与争执自发产生**,同一局面不会每次都一样;我们只提供"舞台与角色",不编排台词。

**聊天节奏:与落子回合解耦,像真实茶馆(关键)**
聊天**不是每手棋触发一次**,而是一个**独立运行的对话循环**,有自己的时间线:
- **多种刺激驱动,而非回合驱动**:落子只是众多"话头"之一;长考、妙手、漏着、连败、冷场太久、你开口说话、上一个话题没聊完……都可能起话头或续话。
- **节奏自然**:有时全场安静各想各的;有时俩人就一步棋你一句我一句争个没完;有时棋局平淡,他们就飘去聊别的(行业、往事、家常)。由"热度/张力"信号 + LLM 决定**此刻谁说、说不说、要不要接着聊**,不是齐刷刷每人一句。
- **话题会漂移也会拽回**:闲篇聊嗨了能继续,真出关键棋手又会被棋拽回来——和真人围观一模一样。
- **成本护栏**:设最小静默间隔与每分钟发言上限,避免无限刷屏与 token 失控;冷场由轻量本地逻辑兜底(无需每次都唤起 LLM)。
- **集中式发言调度 + 规则优先(深度研究修正项)**:由一个**中央"发言选择器"**统一决定 next-speaker,而非各角色各自抢话;**能用简单规则就别用纯 LLM 调度**(更可靠、更省钱)——用"热度/张力 + 角色相关度 + 最近发言惩罚"加权打分选谁开口(类比 Valve Response System 的加权匹配 / AutoGen GroupChatManager 的集中管理)。并把"**谁说话**(next-speaker)"与"**这句说给谁**(addressee:回玩家?接某角色的话?)"**分开建模**,让对话指向清晰、不各说各的。

**长期记忆子系统(核心需求,跨会话):**
- **存什么**:每个角色一份记忆,内容包括——你的棋风/惯用开局/反复犯的毛病、历史战绩与名局、聊过的话题与"梗"、角色对你的态度演变、上次约定("说好这次要改掉漏士这毛病");**以及角色彼此之间的关系与旧账**("上局这步又被老炮儿抬杠""教练总向着你"),让拌嘴有来由、跨局延续。
- **怎么存**:对话/对局结束时,LLM 对本次互动做**摘要 + 抽取关键事实**,写入 SQLite 的 `persona_memory` 表(角色 id、类型 episode/fact、内容、关联对局、时间、热度)。
- **怎么用**:每次该角色开口前,**检索注入**——按"近期 + 相关"取若干条记忆拼进 system prompt(个人单机数据量小,先用 recency + 标签/关键词检索;若需更准再加轻量嵌入语义检索)。检索打分对齐业界事实标准 `score = recency(指数衰减) + importance + relevance(嵌入相似度)`。
- **反思层(深度研究修正项,重要):** 在"摘要+写库+检索"之外,加一层**周期性反思(reflection)**——每局结束(或积累到 N 条事实)时,让 LLM 把零散记忆**抽象成更高层洞见**("这玩家逢残局必急躁""他最近明显在练当头炮"),作为高权重记忆存回。Generative Agents 消融实验证明:缺这一步会**可测量地**降低角色可信度与一致性。这是当前设计最明确的缺口。
- **(可选增强)情绪维度检索**:检索时把"当前情绪/气氛"作为一个因子(Emotional RAG),有助维持口吻脾气一致;证据为论文级、非共识,列为后期可选。
- **效果目标**:开局它会说"老规矩又走中炮?上回你这布局中盘总崩";你赢了它记得"比上周强多了,士角炮那毛病改了"。**像老棋友,不是每次重置的机器人**。

### 5.4 诊断 / 成长分析引擎
- **逐步标注**:每一步对比引擎最佳着,算丢分(centipawn loss);按 **阶段(开局/中局/残局)× 主题(漏着/丢子/错失杀棋/子力失调/缓手)** 打标签。
- **弱点画像**:跨对局聚合 → 雷达图 + 排序的"高频弱点"(如"残局兵法薄弱""中局易丢子")。
- **针对性训练(补齐能力)**:
  - 复盘题:从你**自己败局**的关键失误局面生成"该走哪"练习。
  - 专项陪练:AI 在你薄弱场景(某开局/某残局型)反复与你对练。
- **成长分析 / 历史对比**:每局存指标(准确率/ACPL、各阶段失误率、估算 Elo、开局倾向)→ 时间序列**成长曲线**;选两个时间段对比,LLM 生成"成长轨迹 + 仍存缺陷"的自然语言报告。

### 5.5 棋谱与复盘
- 每局自动存档(着法序列 + 各步评分 + 标注 + 对话记录)。
- 复盘:逐步回放、引擎评分曲线、变着树(分支研究)、悔棋。
- **导入/导出**标准格式,与其他象棋软件互通。
- 棋钟计时(可选开关)。

## 6. 数据模型(SQLite,概念级)

- `games`:对局元信息(时间、模式、对手设定、结果、估算 Elo)。
- `moves`:每步(对局 id、序号、着法、FEN、引擎评分、丢分、标注标签)。
- `messages`:对话/点评记录(对局 id、角色 id、文本、音频引用、时间)。
- `persona_memory`:角色长期记忆(角色 id、类型 episode/fact、内容、关联对局、热度、时间)。
- `weakness_profile`:弱点画像聚合(主题、阶段、严重度、样本数、更新时间)。
- `growth_metrics`:逐局指标快照(用于成长曲线与历史对比)。

数据全本地、可一键导出。

## 7. 接口与数据流(关键路径)

**一步棋的实时流程(WebSocket):**
1. 前端发送用户着法 → 后端校验合法性、落库 `moves`。
2. 引擎管理分析局面(诊断用最佳着 + 控盘用 MultiPV 候选)。
3. 诊断引擎给本步打分/标注(后台,不阻塞)。
4. 导演控制器据模式 + 心理代理信号,从候选中**选出 AI 着法** → 落库、推送前端。
5. 落子只是给"聊天循环"投递一个事件(见下),不直接、不必然触发发言。
6. 局末:汇总指标写 `growth_metrics`、更新 `weakness_profile`;LLM 生成对局小结并更新各角色 `persona_memory`,并触发**周期性反思**把零散记忆抽象成高层洞见存回。

**聊天循环(独立时间线,与落子解耦):**
- 一个常驻循环维护"话头队列 + 热度/张力 + 静默计时"。落子、长考、妙手/漏着、连败、你开口、冷场超时、上个话题未了 …… 都作为**刺激事件**投入,但**是否发言、谁发言、聊几句、聊棋还是闲篇**由热度信号 + LLM 决定。
- 触发发言时:取最近聊天上下文 + 当前局面 + 该角色记忆(对玩家/对彼此的态度) → LLM 生成(允许与引擎评分相左)→ 云 TTS → 推送弹幕 + 语音 → 写 `messages`。可顺势续成多轮你来我往。
- 护栏:最小静默间隔 + 每分钟发言上限;冷场兜底用轻量本地逻辑,不必每次唤起 LLM。

**语音对话流程**:前端采音 → 云 STT → 文本作为一个刺激投入聊天循环(带记忆上下文)→ LLM 回复 → 云 TTS → 播放。`VoiceProvider` / `LLMProvider` 接口封装,便于未来替换。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 控盘"放水"被一眼看穿 | 防穿帮规则:禁送大子、限单步让分、失误藏进合理变化、让步分散;以胜率带而非固定结果为目标。 |
| 开源象棋规则库成熟度不足 | 优先选活跃维护的库;以 Pikafish 局面校验兜底;复杂规则(长将长捉判负)单独测试。 |
| 云语音/LLM 延迟影响实时观棋弹幕 | 点评走流式 + 并发;语音可异步补播;UI 先出文字再补声音。 |
| 角色记忆膨胀、检索变差 | 记忆带热度与衰减,定期摘要归并;个人单机数据量小,必要时再上嵌入检索。 |
| token 成本 | 个人用量有限;点评短、按需触发(非每步必评);本地缓存常用提示。 |
| **角色"人设趋同"**(同模型套不同 prompt 表征雷同) | 用机制制造差异(按棋力档给不同深浅/含噪的引擎读数),不只靠 prompt;上线做盲测验证可区分度。 |
| **涌现式群聊脆弱**(记忆检索失败、幻觉、协调断裂) | 护栏不可省:集中式发言调度 + 检索注入 + 反思层 + 静默/限频;关键事实校验后再让角色引用。 |
| **人设保真 vs 事实正确的此消彼长** | 引擎管棋力、LLM 管表达的分工已化解大半;功能性场景(诊断/教学)主动压低人设戏份("deflanderization")。 |
| Pikafish/权重的平台与许可证 | 实现期核对引擎与 NNUE 权重的开源许可证及各平台二进制可用性。 |

## 11. 实现里程碑(仅为构建顺序,功能不阉割)

- **M1 核心对弈闭环**:棋盘交互 + Pikafish 接入 + 导演控盘(陪练/拟人) + 棋谱存档与复盘。
- **M2 智能分析层**:逐步诊断 + 弱点画像 + 针对性训练 + 成长曲线 + 历史对比。
- **M3 角色与语音**:AI 棋手人设 + 2-3 观棋者(各帮各踩) + 角色长期记忆 + 全程云语音。

三块全部交付后即为完整产品;里程碑只决定先后,不缩减范围。

## 13. 最佳实践对照与设计依据(深度研究结论)

2026-06-19 做了一轮全网深度研究(27 个一手来源、124 条声明、25 条经 3 票对抗式验证)。结论:**本设计在架构层面高度契合工业界与学术界最佳实践**,并据此补强了上文标注"(深度研究修正项)"的若干处。

**已被一手证据验证的设计(高置信度):**
- 长期记忆"摘要写库 + 检索注入" = Generative Agents 记忆流范式的子集;检索打分 recency+importance+relevance 是事实标准。〔Park et al. 2023, UIST, arXiv 2304.03442〕
- 涌现式群聊、不写死规则,可信社交行为能从个体推理涌现(但**脆弱**,护栏必留)。〔同上〕
- 聊天与回合解耦、刺激驱动、系统决定"说不说" = Valve Source 引擎 Response System(概念 + 状态快照 → 加权打分)。〔Valve Developer Wiki: Response System〕
- 集中式 next-speaker 调度、规则优先于纯 LLM。〔AutoGen GroupChatManager 文档〕
- "谁说话 / 说给谁"应分开建模。〔Multi-Party Conversational Agents: A Survey, arXiv 2505.18845〕
- 引擎管棋力 + LLM 管表达 = 化解"人设保真 vs 事实正确"张力的正确手段。〔CPDC 2025, arXiv 2510.13586〕

**据研究新增/上移的修正项:** ①补"反思(reflection)"层 ②用机制(差异化引擎读数)而非纯 prompt 制造角色差异 ③集中式发言选择器 + addressee 分离 ④导演优化目标从"防穿帮"上移到"防流失/参与度"(EDDA 思路,MDPI Appl. Sci. 2025)。

**未覆盖 / 待实现期验证的开放问题:**
- 给每个棋友不同档案 prompt,实际能否产出可区分的棋评(人设趋同风险)——上线做小规模盲测。
- 低成本约束下,reflection 的最优触发频率(每局?每 N 条事实?)。
- 中国象棋实时解说的角色化多解说员配合,本批未搜到专门一手资料,需单独补研。
- 拟人对手:国际象棋有 Maia(开源拟人引擎,按人类棋力预测人类着法),中国象棋无现成等价物,故仍以 Pikafish MultiPV 采样近似;DDA 放水幅度多大不被察觉,需实测。
